# Using and developing gosubc

**Source:** https://github.com/arran4/go-subcommand (consult current README, AGENTS.md and `gosubc help` before commands). The embedded upstream `skills/gosubc/SKILL.md` currently lacks standard frontmatter and references `format-source-comments`; the actual source exposes `gosubc format` with `--inplace`.

## Choose the operation
- Existing project: identify its pinned generator invocation (`//go:generate`, README, Makefile, CI). Do not substitute `go install ...@latest` when reproducible versioning is required.
- Inspect definitions: `gosubc list` and `gosubc validate`; prefer `go run ./cmd/gosubc list` and `... validate` when working inside the source repository.
- Format comments: `gosubc format` previews by default; `gosubc format --inplace` writes and must follow review of output.
- Generate: use the project's invocation. When working on gosubc itself, `go run ./cmd/gosubc generate --clean` refreshes generated source and removes version-marked stale generated files. Do not run `--clean` in an unrelated project without checking the project's generation policy.

## Invariants
1. Never directly patch files with a `Code generated ... DO NOT EDIT` header; change comment directives, templates or generator, regenerate, then inspect the diff.
2. The generated application's code must not depend on importing `github.com/arran4/go-subcommand`. It is a build-time generator.
3. Parameter annotations, aliases, parent flags, custom parser and generator hooks, positional/variadic bindings and help routes are part of one parser+template contract. Inspect README and current generation output; do not assume Go's `flag` handles all argv parsing.
4. The plus/minus and optional-value flag backend remains under active design (e.g. issues #464/#401 and PRs #505/#511). Distinguish `+a`, `-a`, `--ab`, `++ab` and `--` rather than asserting unmerged semantics.
5. For generator or parser changes, extend inspectable `templates/testdata` TXTAR scenarios with `input/` and `expected/` entries. Keep complete expected output; use `fstest.MapFS` for in-memory unit tests where filesystem semantics are not under test.
6. Check README, generated usage/manpages and isolated example modules, not only the root module. Root checks: `go test ./...`; example checks from each example directory. Avoid changing golangci-lint versions to hide failures.
